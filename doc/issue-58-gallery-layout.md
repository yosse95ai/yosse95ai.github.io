# Issue #58 ギャラリーの「穴あき」レイアウト — 原因と対応プラン

対象: `src/components/organisms/PhotoGrid.astro`
関連 issue: [#58 ipad でギャラリーのレイアウトがぐちゃぐちゃ](https://github.com/yosse95ai/yosse95ai.github.io/issues/58)

## 1. 症状

| 端末 | 症状 |
| --- | --- |
| iPhone (Safari) | 2 列表示。右列の先頭が写真 1 枚分（約 135px）下にずれ、右上に穴が空く |
| iPad (Safari) | 4 列表示。1 列目だけが上端から始まり、2〜4 列目の先頭が 200〜350px 下にずれる |

どちらも「列の先頭に余白が挿入される」という同じ症状。

## 2. 原因

**CSS マルチカラム（`columns-*`）のフラグメンテーション実装が WebKit と Chromium で異なることが原因。**
WebKit は列の分割位置で生じた「余り」を、直前の列の末尾ではなく **次の列の先頭に持ち込む**。

該当コード（`PhotoGrid.astro`）:

```
27: <div class="columns-2 sm:columns-3 md:columns-3 lg:columns-4 gap-3">
31:   class="break-inside-avoid overflow-hidden rounded-2xl mb-3 photo-item ..."
```

- 各写真は `overflow-hidden` + `break-inside-avoid` により分割不可（monolithic）な塊になる
- 列に収まらない塊は次の列へ送られるが、WebKit ではその際の余白が次の列の先頭に残る
- Chromium は仕様どおり列境界の余白を切り捨てるため、同じ HTML/CSS でも崩れない

## 3. 計測による裏付け

Chromium 141 と WebKit 26 の 2 エンジンで、各列の「先頭の余白（topGap）」を実測した。

| 検証 | 結果 |
| --- | --- |
| Chromium / 390・430・768・820・1024・1180・1440px | 全列 `topGap=0`。崩れなし（＝Chrome では再現しない） |
| WebKit / 実物と同じ画像・同じ CSS 構成の再現ページ | 2 列目の先頭に **12px** の隙間 |
| WebKit / `margin-bottom` を 12px → 40px に変更 | 隙間も **40px** に変化 → **隙間の正体は直前の列の最後の要素の下マージン** |
| WebKit / `margin-bottom: 0` にして間隔を要素内側の `padding-bottom` で確保 | 隙間 **0**。列の振り分けも Chromium と一致（7/7） |

### 原因ではないと確認できたもの

いずれも単独で外しても、また組み合わせても隙間は消えなかった。

- `loading="lazy"`（`eager` に変えても再現）
- スケルトンの `min-height: 120px`
- `photo-item` のフェードインアニメーション（`opacity` / `translateY`）
- 画像ロード前後でのレイアウト再計算（grid 高さは初期とロード後で一致）

### iOS 実機との差

本環境で用意できた WebKit 26 (WPE) では漏れ量が 12px（マージン分）にとどまり、実機の 200〜350px という大きな漏れまでは再現できていない。
**バグの種類（列の先頭に余白が漏れる）は同一と確認できたが、漏れ量の完全再現はできていない。**
そのため最終確認は実機で行う必要がある（プラン 6）。

## 4. 修正方針の選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. 最小修正** | `mb-3` を廃止し、間隔を要素内側の `padding` で確保 | 差分は数行。WebKit 26 では効果を確認済み。ただし iOS の大きな漏れに効くかは未確認 |
| **B. 推奨** | マルチカラムをやめ、列コンテナ方式にする。画像の縦横比はビルド時に既知（Astro の `ImageMetadata`）なので、列への振り分けもビルド時に確定できる | フラグメンテーションを使わないため、この種のバグが構造的に発生しない。見た目は現状維持 |
| **C. 代替** | 均一グリッド（`aspect-ratio` + `object-fit: cover`） | 最も堅牢だがトリミングが入り、デザインが変わる |

B はブレークポイントごとに列数が変わるため、「ビルド時に 2/3/4 列それぞれの振り分けを確定し、CSS で切り替える」か「振り分けだけ極小スクリプトで行う」かの選択が残る。ここは実装時に決める。

## 8. 実施記録

### サイクル 1: 案 A（間隔を `margin-bottom` から外側要素の `padding-bottom` へ）

変更内容（`PhotoGrid.astro`）:

- 写真 1 枚を「外側 = `break-inside-avoid pb-3 photo-item`」と「内側 = `overflow-hidden rounded-2xl skeleton skeleton-img`」の 2 段構成にした
- 間隔は外側の `pb-3` で確保し、`mb-3` を廃止（列の分割位置に漏れるマージンをなくす）
- 角丸・影・スケルトンは内側に置き、見た目は変更なし
- 併せて `.photo-item.skeleton-img > img` → `.photo-item .skeleton-img > img`

計測結果（各列先頭の余白 `topGap`。実際のビルド出力のマークアップを使用）:

| 幅 | 列数 | WebKit 修正前 | WebKit 修正後 | Chromium 修正前 | Chromium 修正後 |
| --- | --- | --- | --- | --- | --- |
| 390px | 2 | 0 / 0 | 0 / 0 | 問題なし | 問題なし |
| 430px | 2 | **0 / 12** | 0 / 0 | 問題なし | 問題なし |
| 768px | 3 | **0 / 12 / 0** | 0 / 0 / 0 | 問題なし | 問題なし |
| 820px | 3 | **0 / 12 / 0** | 0 / 0 / 0 | 問題なし | 問題なし |
| 1024px | 4 | **0 / 0 / 0 / 12** | 0 / 0 / 0 / 0 | 問題なし | 問題なし |
| 1180px | 4 | **0 / 0 / 0 / 12** | 0 / 0 / 0 / 0 | 問題なし | 問題なし |
| 1440px | 4 | **0 / 0 / 0 / 12** | 0 / 0 / 0 / 0 | 問題なし | 問題なし |

- WebKit: 7 幅中 6 幅で発生していた漏れが **全幅で 0** になった
- 列への振り分けも WebKit と Chromium で一致するようになった（修正前は 430px で 8/6 と 7/7 に分かれていた）
- 副作用の確認: Chromium で実サイトを 7 幅計測して崩れなし、修正前後のスクリーンショットで見た目の差もなし
- `bun run test`（86 件）/ `bun run check`（0 errors）/ `bun run smoke` すべて成功

### 残っている確認（必須）

WebKit 26 では漏れ量が 12px だったのに対し、実機は 200〜350px 漏れていた。**同じ原因の軽い版を潰したことは確認できたが、実機の重い版が消えるかは未確認。**
`deploy.yml` は master への push でのみ動くため、実機確認は PR をマージした後の本番サイトで行う。

- 直っていれば issue #58 をクローズ
- 直っていなければ案 B（マルチカラムをやめる）へ進む


### サイクル 1 の結果: 実機では直らなかった

PR #82 をマージして実機で確認したが、穴は残っていた。
つまり iOS/iPadOS Safari で漏れているのは **マージンだけではなく、フラグメンテーションそのものが原因** だと確定した。
WebKit 26 で観測できた 12px のマージン漏れは、同じ根本原因の軽い症状に過ぎなかった。

→ 案 A では不十分。案 B（マルチカラムをやめる）へ進む。

### サイクル 2: 案 B（マルチカラムを廃止し、列ごとの要素に振り分ける）

変更内容（`PhotoGrid.astro`）:

- `columns-*` を廃止。`.photo-grid` を flex にし、列ごとの `.photo-col`（flex 縦積み）に写真を入れる
- 列への振り分けは「短い列から詰める」方式。各列の高さは **ビルド時に埋め込んだ縦横比（`data-ratio`）と実際の列幅** から計算するので、画像の読み込み完了に依存しない（レイアウトシフトが起きない）
- 振り分けは `is:inline` の同期スクリプトで実行する。バンドルされた `<script>` は defer 扱いになり 1 カラム → 多カラムのちらつきが出るため
- 列数は 2 / 3 / 4（境界は 640px / 1024px。Tailwind の `sm` / `lg` と同じ）
- JS 無効時は CSS のフォールバックで 1 カラムになる（崩れることはない）
- HTML 上の写真の並びは `img.json` の order 順のまま（既存のスモークチェックはそのまま通る）

計測結果（各列先頭の余白 `topGap` / 列数）:

| 幅 | WebKit | Chromium | 列数 |
| --- | --- | --- | --- |
| 390px | 全列 0 | 全列 0 | 2 |
| 430px | 全列 0 | 全列 0 | 2 |
| 768px | 全列 0 | 全列 0 | 3 |
| 820px | 全列 0 | 全列 0 | 3 |
| 1024px | 全列 0 | 全列 0 | 4 |
| 1180px | 全列 0 | 全列 0 | 4 |
| 1440px | 全列 0 | 全列 0 | 4 |

- **WebKit と Chromium で列数・振り分け・grid の高さが完全に一致した**（レイアウトを自前で決めているため、エンジンのフラグメンテーション実装に依存しなくなった）
- 画像ロード前後で高さが変化しないことも全幅で確認
- JS 無効時は全幅 1 カラムで崩れなし
- 修正前後のスクリーンショットを比較し、余白・角丸・影は同一。列への振り分け結果は変わる（短い列から詰めるため）
- `bun run test`（86 件）/ `bun run check`（0 errors）/ `bun run smoke` すべて成功

回帰防止（プラン 7）:

`scripts/smoke-build.ts` に「ギャラリーが `columns-*` を使っていないこと」「`data-photo-grid` があること」「`data-ratio` が img.json の件数だけあること」の検査を追加した。
マルチカラムを混入させた dist でスモークが失敗することも確認済み。
